# `issue-workflow` 走读

## 人话结论

一个全新的 Codex 或 Claude Session，只拿到一个远端 Issue 编号，应该能读到正确的 Skill、在当前这台机器上实际可用的 GitHub 能力里恢复合同、判断自己是执行叶子还是协调子树、按风险决定审查强度，并在结束时回到父级找证据。本文记录这条路径的静态走读结果，以及哪些部分**还没有**真实运行证据。

自动化部分见 `tests/workflow-routing.test.ts`；本文只覆盖测试无法断言的内容：一个新 Session 实际会读到什么、在每个岔口会走哪条边。

## 一、三种模式的入口路径

Agent 系统入口只负责识别三种情况并加载能力，详细状态机在 Skill 内。

```text
情况 A：手上有一个叶子 Issue
  入口 → issue-workflow → 第三节判定为叶子 → 第五节 → issue-delivery → Draft PR
                                          → 第七节 → pr-integration（只交回事实）
                                          → 第九节回收：有父级则收父级，无父级则收本 Issue 自己

情况 B：手上有一个父 Issue
  入口 → issue-workflow → 第三节判定为父 → 第六节
        ├ 正文已失真 → issue-contract-compaction → 回第六节
        ├ 维护子图   → objective-to-issues（增量切片属于维护，不重新请求建图授权）
        ├ 自己执行   → 回第三节按叶子模式推进
        └ 确需并行   → orchestrated-collaboration + 当前真实后端

情况 C：手上没有 Issue
  入口 → 经营总账与未满足诉求（operating-ledger-maintenance 维护）
       → adaptive-problem-solving 选出瓶颈
       → 形成有界 Issue（需要任务图时经 objective-to-issues）
       → 才进入 issue-workflow
  若误入 issue-workflow，它按第四节沿同一条路由退出，不遍历仓库队列。
```

## 二、新 Session 的发现依据

两个运行端都靠 `description` 匹配当前情境，因此三种模式的触发词必须出现在 `issue-workflow` 的 `description` 里，而不只是正文中。当前 `description` 同时包含：

- 叶子触发：「手上是叶子 Issue 就按合同端到端交付」；
- 父触发：「手上是父 Issue 就在当前授权内维护并推进自己的子树」；
- 决定触发：「用 Issue 前缀编号绑定短回复，并在转呈前验收请求协议」；
- 关闭触发：「逐项授权或三条件预授权谓词覆盖时带回执关闭」；
- 反向触发：「手上没有具体 Issue 时不要用它遍历仓库队列或自行挑活」；
- 退出语义：「退出时也不保留永久协调者身份」。

`tests/workflow-routing.test.ts` 断言每个 Skill 的 `description` 同时含中文和英文触发说明，因为两个运行端的匹配语言不一定与正文一致。

显式入口：Codex `$issue-workflow`，Claude `/github-collaboration:issue-workflow`。

## 三、验收场景走读

下表的「落点」是产生该行为的具体规则位置，测试逐条断言这些落点存在。个别场景另有**反向断言**（`mustNotContain`），用来证明规则**没有**用会过期的方式表达——例如把某个客户端的命令写死进正文，规则就会随那个客户端的接口一起过期。

### 1. 长讨论压缩时不丢授权、阻塞、决定

**输入**：父 Issue 正文停留在三周前，关键授权和两条阻塞只在评论里。

**走读**：第六节第 2 步判定正文已失真 → `issue-contract-compaction`。它先读远端并记录更新时间，生成新正文后**紧接写入前再读一次**；八项必须保留的内容中，授权、阻塞、决定优先级最高，宁可保留原文也不概括。评论一条不删。中间产物只放在本次会话临时工作区，不在仓库里建草稿目录。

**为什么不会丢**：删除只允许作用于重复表述、已标注替代关系的旧结论和纯过程噪声；被替代的结论必须写清被什么替代。

**落点**：`issue-contract-compaction` 第二、三、四、五节。

### 2. 空子项但父级未完成

**输入**：最后一个子 Issue 已合并并关闭，父级还有两条成功条件没有证据。

**走读**：第九节先确定回收对象（此处有父级，故为父级），逐条找证据 → 命中「没有可执行子项，但成功条件未满足」→ 判断缺的是切片、依赖还是负责人决定 → 补规划（回第六节）、报告阻塞或提出一次决定。

**为什么不会误判完成**：第九节明确列出「子项列表为空、子 PR 已合并、Worker 已回执、子 Issue 已关闭、旧 head 检查通过」都不能单独证明成功条件已满足。`pr-integration` 把这些**作为事实交回**而不自行推断，`objective-to-issues` 同样只交回「缺哪一类」，两者都不作完成判定。

**落点**：`issue-workflow` 第九节、`pr-integration` 第六节、`objective-to-issues` 第七节。

### 2b. 顶层叶子（没有父级）在获准合并后的终点

**输入**：一个独立的顶层 Issue，没有父级也没有子项，PR 已按明确授权合并。

**走读**：第三节按「没有未完成子 Issue」判为叶子——它并不要求存在父级。第九节先确定回收对象：本 Issue 没有父级，因此回收对象是**它自己的成功条件**。逐条找证据后落在三种出口之一：

- 全部满足且已有逐项关闭授权，或交付／实验／摩擦类对象同时满足三条件预授权谓词 → 带逐条证据与授权来源回执关闭本 Issue；
- 全部满足但既无逐项关闭授权也不满足预授权谓词 → 明确停止：报告证据、说明关闭权归谁、请求一次关闭决定，不自行关闭；
- 仍有未满足条件 → 报告阻塞或提出一次决定。

**为什么需要这条分支**：如果第九节无条件「回到父级」，一个没有父级的叶子在合并后就没有终点——既不核对自己的成功条件，也没有关闭或停止的出口。测试用 `reclaim → close` 和 `reclaim → stop` 两条状态转移断言这条出口存在。

**落点**：`issue-workflow` 第九节「先确定回收对象」与收口表前两行；`pr-integration` 第六节「有父级时是父级，没有父级时是本 Issue 自己」。

### 2c. 三条件关闭预授权

**输入**：交付、实验或摩擦类 Issue 的成功条件均有远端证据，且没有未消费的负责人动作、开放子项或被依赖的开放事项。

**走读**：第九节先检查逐项授权；没有时核对三条件谓词。全部成立就引用 [#44 规则回执](https://github.com/Eridanus117/agent-control/issues/44#issuecomment-5255408590) 留收口回执并关闭。目标与诉求层、父目标、产品取舍或授权边界类 Issue 被明确排除；对象类型、关系或证据拿不准也按谓词未满足处理，保留决定门。

**替代关系**：它替代「成功条件满足后仍一律逐次索要关闭授权」的默认路径，不扩大合并、安装、删除或产品决定授权。

**落点**：`issue-workflow` 第九节「三条件关闭预授权谓词」与收口表前两行。

### 3. 低风险叶子不进入重型审查

**输入**：一个只改自己拥有的文档、可回退、不涉及契约的叶子 Issue，合同里已经写明实施授权。

**走读**：第八节风险表判为「轻」→ 实现者自审 + 可自动化的检查即可。`issue-delivery` 第五节默认直接实现，且因为合同已有实施授权，实现、验证、推送和建 Draft PR 都不再逐个索要批准。

**为什么不会被拉高**：第八节有三条反向规则。最容易被忽略的是第一条——**进入合并阶段本身不是重风险信号**。每个 PR 到合并阶段都需要明确授权，如果把「涉及合并授权」直接当成重风险信号，任何 PR 都会被判为重，轻量路径就实际上不存在了。因此重风险信号被收窄为「合并授权缺失、与当前 head 不匹配、需要一次新决定或会扩大授权」；一份有效的条件式预授权已经覆盖当前 head 时，按改动本身分级。另两条是：不因为「看起来复杂」或「想更稳妥」就升级；已有预授权不重复索要批准。

**落点**：`issue-workflow` 第八节、`issue-delivery` 第五节、`pr-integration` 审查强度分级表。

### 3b. 父模式选择自己执行还是派发

**输入**：父 Issue 下有三个待推进切片。

**走读**：第六节第 5 步既不默认串行也不默认并行，而是核对三个**肯定式的可派发条件**——切片之间**没有**依赖边；能给每个切片**排他**分配文件、分支和远端对象；协调净收益**为正**（派发、上下文恢复、验收和综合的成本低于并行省下的周期）。三条全部成立才派发；任何一条不成立就自己推进，有依赖边时按依赖顺序。三条都写成肯定式，是为了避免「有依赖边」被误读成派发条件。

**为什么不能有默认值**：预设「顺序推进更稳妥」会压低并发吞吐并提高负责人依赖；预设「并行更快」会在写入范围重叠时制造冲突和返工。判据只有那三条，不看 Session 数量、终端是否空闲或额度是否充裕。

**落点**：`issue-workflow` 第六节第 5 步。

### 4. 高风险变化正确升级

**输入**：一个会修改用户级配置和长期依赖判断的切片。

**走读**：第八节命中「重」→ 需要未参与实现的 Agent 做只读复核，并把负责人决定合并成一次。复核者的派发走 `orchestrated-collaboration`，检查项由 `adaptive-problem-solving` 的最终验收检查提供。合并授权仍必须明确指向当前 PR。

**为什么不会自行放行**：第七节写明合并授权只能来自负责人或合同中明确的条件式授权；PR 已打开、CI 通过、审查批准、Worker 回执、子 Issue 关闭都不是合并授权。

**落点**：`issue-workflow` 第七、八节，`pr-integration` 分级表与第五节。

### 4b. 决定请求先验收再转呈

**输入**：执行者交付了一组需要负责人决定的请求，但只有结论，没有维持现状、逐选项比较或可信反方。

**走读**：协调者在转呈前核对五项：备选枚举含维持现状、逐选项比较、推荐与置信、最强可信反方、翻转条件。缺一项就退回重构，既不转呈也不投影为等待负责人。普通授权门仍保持批准／否决／修改边界的真实选项，不为凑格式制造 A／B／C。

**为什么增加这道验收**：负责人原话「这种东西不应该 AI 自己先调研一下吗」；[#9 撤回回执](https://github.com/Eridanus117/agent-control/issues/9#issuecomment-5255799405) 已记录原请求缺少备选比较且协调验收未拦截。

**落点**：`issue-workflow` 第八节「协调者转呈前的协议符合性验收」。

### 4c. 决定编号跨 Issue 唯一绑定

**输入**：同一轮同时存在 `9-D1`／`9-D2` 与 `44-Da`／`44-Db` 两组同格式请求，负责人只回复“同意”。

**走读**：决定编号必须使用 `<Issue 号>-<局部编号>`；短回复携带完整前缀时优先绑定。两组同格式编号并存时，即使评论紧邻其中一组，裸 `B`／“同意”也不得按唯一紧邻消费，必须按完整编号逐条澄清。

**替代关系**：它替代裸局部编号依赖评论顺序或紧邻关系的绑定方式；真实错绑定证据见 [#44 波次回执](https://github.com/Eridanus117/agent-control/issues/44#issuecomment-5255737976)。

**落点**：`issue-workflow` 第八节「请求格式」与「解析自然回复」。

### 5. 纠偏不误停独立分支

**输入**：同一批次里 A 分支的关键假设被负责人推翻；B 分支有独立 Issue 合同和独立写入所有权，结论不依赖那条假设。

**走读**：第十一节先问「推翻了哪一条假设」→ 冻结 A 及与其共享写入范围的路径、冻结会把受影响结论发布到远端的动作 → B 继续并记录这次判断。只有当纠正指向全局不变量、授权本身或共享状态一致性时才整体冻结。

**为什么不默认全停**：第十一节写明「把独立、安全、有明确合同的工作一起停掉，本身就是一次损失」，要求它与继续的风险同样被权衡。同一条边界在 `self-improvement` 第一节（单 Session）和 `orchestrated-collaboration` 第一节（多 Session）各有对应落点。

**落点**：`issue-workflow` 第十一节、`self-improvement` 第一节、`orchestrated-collaboration` 第一节、`issue-delivery` 第九节。

### 6. 一个 GitHub 客户端不可用，但还有已认证候选

**输入**：新 Session 只拿到一个 Issue 编号。它第一次调用某个命令行客户端，得到 not found——那个客户端不在 `PATH`。同一台机器上还有一个已认证、能读写 Issue 正文与评论、也能读到原生父／子关系的 GitHub 集成。

**走读**：第二节把「选用什么读远端」放在「只读三样东西」**之前**。本次需要的语义是正文、评论、状态和原生父／子关系；按第 1 条「按语义选，不按客户端名选」，命令行客户端和那个集成是同一类候选。第 2 条判定这次的 not found 只证明**这一个候选**不可用，于是直接换到已认证集成继续恢复，然后照常进入第三节判定模式。

**为什么不会误判成远端不可用**：第 2 条明确写了「不把它报告成『远端不可用』，也不因此暂停恢复或改从聊天记忆、本地草稿恢复合同」，禁止清单里也单列了「因为一个客户端缺失就宣布远端不可用」。反方向同样被禁止：某个客户端可用，不等于它具备本次所需的全部语义和权限。

**为什么不允许「顺手修好它」**：让那个客户端可用需要安装工具、改 `PATH`、读写凭据或改用户级配置。这些都在禁止清单里——它们是负责人的决定，不是恢复动作；恢复的目标是读到远端事实，不是把本机环境改成某个客户端能跑。

**落点**：`issue-workflow` 第二节「先按所需语义选择远端访问能力」的规则 1、2 与禁止清单。测试用 `client-missing-does-not-block-recovery` 断言这些落点存在，并用反向断言证明正文没有写死任何一个客户端的命令。

### 6b. 没有任何候选能表达所需语义

**输入**：本次要在父 Issue 上建立原生子关系并写回一条决定，但当前只有一个未认证的只读通道。

**走读**：第二节第 3 条命中——所有可用候选都不能表达「原生父／子关系」和「写回」。于是按第八节把缺口合并成一次报告：缺的是哪一项语义、已经试过哪些候选、因此哪些读或写被停住；再按第十一节只冻结受影响的那部分，本 Issue 上不依赖这两项语义的只读推进继续。

**为什么不会被绕过去**：禁止清单挡住了三种典型的绕行——降级到未认证抓取或公开页面解析、把只读能力当成可写用（或写入没真正成功却说成已写回）、把正文里的链接冒充原生父／子关系。三种都会让下一个 Session 从一份看起来完整、实际错误的远端状态恢复合同。

**为什么停的范围不是全部**：第 3 条要求按第十一节冻结，而不是整体停摆；与场景 5 是同一条边界。

**这一节不做状态判定**：第二节末尾写明它只决定用什么读写远端，不决定模式、切片顺序、回收对象或收口结论——那些仍然只属于第九节。因此这条规则不构成第二套状态机。

**落点**：`issue-workflow` 第二节规则 3、禁止清单与收尾段。测试用 `missing-semantics-stops-precisely` 断言。

## 四、路由为什么不成环，以及「唯一驱动者」怎么被证明

三种边分开表达，只有 drive 边参与环判定：

| 边 | 含义 | 约束 |
| --- | --- | --- |
| drive | **段调用**：把当前工作交给目标 Skill 完成那一段并等待段结果 | 必须构成有向无环图 |
| return | 把段结果交回生命周期决定者 | 只允许指向 `issue-workflow`；不是新调用，不参与环判定 |
| reference | 只说明某项判断的正文在哪 | 允许双向 |

这里要分清两件事：**段调用转移的是执行，不是生命周期决定权**。因此段 Skill 拥有 `drive` 边（例如 `issue-delivery` 升级到 `adaptive-problem-solving`）是正常的，它不会因此变成第二个生命周期决定者——模式、切片顺序、回收对象和收口结论始终只由 `issue-workflow` 决定。

`orchestrated-collaboration` 可以指出「子树内的驱动行为由 `issue-workflow` 承担」而不构成环——它没有发生调用。同理 `self-improvement` 引用 `adaptive-problem-solving` 的判据表也只是引用。

但**无环和命名一个 driver 都不足以证明「只有一套状态机」**。真正要防的失败是：某个段 Skill 自己重做一遍完成判定，于是链上出现两套迟早给出不同结论的状态机。这一点靠下面三组断言来证明，而不是靠名称是否出现：

1. **谁能判定**：`lifecycle.decisionPhrasesReservedToOwner` 里的判定语（例如「完成父 Issue」「对每个父级完成门重新找证据」「重新验收父目标」）只允许出现在驱动者正文里；任何其他 Skill 出现即失败。
2. **段的义务**：每个声明了 return 边的段 Skill 必须写明「只返回事实与段结果」，且不得对驱动者声明 drive 边——它只能交回，不能反向驱动。
3. **状态机闭合**：驱动者的每一条状态转移都要在正文中找到证据字符串；不允许有不可达状态或死角（非终止状态必须有出边）；并且 `reclaim` 必须同时存在 `close` 与 `stop` 出口，否则没有父级的顶层叶子就没有终点。

同时保留原有的双向比对：声明了但正文没写、正文写了但没声明，都会失败。

**这套断言不覆盖什么**：它检查的是判定归属和状态机结构，不是自然语言语义。它无法证明某段散文在语义上没有隐含另一种判定，只能证明保留判定语没有出现、段义务已写明、状态转移逐条有证据。语义层面仍依赖复核。
